# Discussion questions

Written answers to the four questions of the exercise, with the evidence they rest on. Numbers are the ones in the [solution brief](solution-brief.md) and the [final report](../evidence/REPORT.md).

## Limits of the current solution

**Modeling.** The delivered detectors classify causal caller audio. The API accepts up to 8 s; both selected encoders use 4 s of internal context (Whisper crops the mel features, Cohere the waveform). The selected benchmark protocol scores once per eligible pause at 200 ms of silence; the endpointing policy (threshold, action delay, timeout) lives in the caller. Neither selected model receives explicit conversation context: the agent's own question (a request for an MC number invites a pause-rich digit string), the conversation so far, or an explicit transcript. ASR pretraining can still encode semantic cues in the audio representation. The public model that beats ours (LiveKit v1, 543 ms) combines semantic and acoustic branches that both start from audio, without an intermediate transcript ([architecture](https://livekit.com/blog/solving-end-of-turn-detection)); our best CPU model waits 756 ms and our GPU model 615 ms, and the remaining gap is endpointing quality, not latency. The encoders we use were pretrained for transcription with bidirectional attention inside the window; they see nothing after the decision point, but they also carry no streaming state, so every score is a full-window recompute. A causal streaming encoder would make the per-hop cost incremental; we measured a causal candidate (Voxtral) but paused it before it was evaluated.

**Data.** Labels are heuristic: a training row is an audio prefix cut inside a real pause and labelled by what the speaker did next, with rules calibrated against existing human annotations (TurnBench, AppTek dual-channel events). No new human-annotated corpus was built and the listening audits we prepared have zero human judgements, so label noise is bounded only indirectly. The training mixture is English role-play and read speech over VoIP and synthetic telephony; real HappyRobot calls (accents, barge-in, hold music, DTMF, noisy cabs) are not represented. The public benchmark was inspected repeatedly and its policies fitted on it, so our numbers are optimistic relative to a blind test; the only strict external set (Krisp) is licensed for evaluation only and its readouts were omitted from the final campaign.

## Audio, text, multimodal, or a VAD

A VAD answers "is there speech" and needs 500 to 800 ms of silence to be safe; it cannot tell a breath before a digit string from the end of a sentence. Every model here beats a silence timer because it reads what the audio contains at 200 ms of silence: prosody (falling pitch, lengthened final syllable), speech rate, hesitation particles, and the texture of the pause itself.

Text alone arrives late and stripped of that prosody: the transcript of the last words is available only after the ASR commits it, typically hundreds of milliseconds after the audio, and a transcript cannot distinguish "four two seven..." trailing off from "four two seven." Text is nevertheless the cheapest source of semantics, and the agent's own last utterance is free: it is known before the caller speaks. We implemented that as an optional conditioning branch (`use_context`, the previous agent text hashed into n-gram ids) and evaluated it as an ablation; on the public benchmark, whose adapter sends audio only, it could not be exercised, so the delivered models run audio-only.

One next experiment is to add explicit context: audio for timing and prosody, the agent's question and a partial transcript for meaning. This is a hypothesis to test against our audio-only control, not an established explanation of the gap to LiveKit. LiveKit's semantic branch projects audio into a language model; its acoustic branch captures timing and prosody. The practical constraints are latency (the semantic branch must not wait for the final transcript) and serving (a text encoder adds a second model to keep warm), which is why we would start with the agent-side text that costs nothing at inference.

## Can a transcriber do this task

Yes, and that is what the delivered models are. Both are ASR encoders with the decoder removed and a small head on top: Whisper-base (74 M) for the CPU service and the Cohere Transcribe Fast Conformer encoder (1.9 B) for the GPU service. The recipe: take the pretrained encoder, keep its front-end, feed it the causal audio prefix, pool the frame embeddings with attention, and train a binary end-of-turn head; adapt the encoder with LoRA when it is large (r = 16 on all 48 Cohere layers) and fully otherwise. Fine-tuning the representation is what matters: the Cohere encoder frozen with a trained head waits 789 ms; adapted with LoRA, 636 ms; the same adaptation later became the teacher whose soft targets moved Whisper-base from 897 to 802 ms in the controlled study.

Two things a transcriber does not give for free. First, the decoder's transcript is not needed for the decision, so we drop it and the latency it would add; a Parakeet-style CTC or transducer encoder would serve the same way, with the advantage that its streaming variants keep state between hops. Second, ASR pretraining does not see silence structure as a target: the pause texture in our training audio had to be rewritten explicitly (gated zeros or room noise at the row's floor, independently of the label) before the models stopped using "what a pause sounds like" as a shortcut.

## Integration in a voice agent

The scorer is stateless and the turn-taking loop lives in the agent, next to the VAD and the audio ring buffer:

1. The VAD marks the start of a pause. At 200 ms of an eligible pause, the agent sends the last 8 s of the caller's audio once using `POST /v1/eot` with a PCM16 body, `score_mode="score_point"` in the endpointer, and `deadline_ms` set to the remaining application budget and receives `p_eot` and timings.
2. An endpointer keeps the state (`eot.eval.policy.Endpointer` is the reference): the first score above the threshold latches, the commit happens at `max(action_delay, first crossing)`, a maximum timeout commits regardless, and any resumed speech invalidates the pending generation so a late response cannot trigger a reply after the caller continued.
3. On commit the agent releases the transcript to the LLM and starts TTS. Both selected models return an empty `p_fvad` field; they provide no future-speech probability for speculative LLM prefill. That would be a future extension requiring a trained and validated auxiliary head and rollback when the caller resumes.
4. The service runs beside the media server, on CPU for the Whisper model (8 threads, 8 in-flight requests, the current measured p95 is recorded in the [post-review verification](../evidence/deployment/post-review/README.md)) or on a GPU for the Cohere model (batched execution, 2 ms batching window). Capacity is bounded: a 503 or a missed deadline falls back to the conservative silence timeout rather than to a retry queue.
5. Every decision is logged with model and policy versions, the score trajectory, timings, and whether the caller resumed, which is the input to the monitoring and feedback loop described in [operations.md](operations.md).

The action delay and threshold should depend on the agent's question (a yes/no question commits faster than a request for an address); that is the first place the agent-side context enters even before it is fed to the model.
